Railway runs the Gateway for you and serves the [Control UI](/web/control-ui) on a public HTTPS domain. This is the easiest "no terminal on the server" path: after the first deploy, every OpenClaw setting is changed from the browser.

There are two ways to get there:

- **Deploy from your repository** (recommended): the repo ships `railway.json`, `Dockerfile.railway`, and a first-boot bootstrap under `deploy/railway/`. Railway builds a thin image on top of the official OpenClaw image and the bootstrap writes a working `openclaw.json` to the volume.
- **One-click template**: the community template, configured through Railway variables.

## Deploy from your repository

### What the repo provides

| File                           | Purpose                                                                                                                                      |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `railway.json`                 | Config as code: builds `Dockerfile.railway`, requires a volume at `/data`, probes `/startupz`, restarts on failure, rebuilds only when these files change |
| `Dockerfile.railway`           | `FROM ghcr.io/openclaw/openclaw:<version>` plus the bootstrap; builds in seconds instead of compiling the monorepo                            |
| `deploy/railway/entrypoint.sh` | Hands the root-owned Railway volume to the unprivileged `node` user, keeps auth-profile key material on the volume, then starts the Gateway   |
| `deploy/railway/bootstrap.mjs` | First boot: writes a minimal, schema-valid `openclaw.json`. Every boot: adds a new Railway or custom domain to the Control UI origin allowlist |

The bootstrap never rewrites a setting you changed in the Control UI, and it leaves any config file it cannot parse as plain JSON untouched.

### Steps

<Steps>
  <Step title="Push the repository">
    Push this repository (or your fork) to GitHub. Railway deploys from the branch you select and rebuilds when `railway.json`, `Dockerfile.railway`, or `deploy/railway/**` change.
  </Step>

  <Step title="Create the service">
    In the Railway dashboard choose **New Project → Deploy from GitHub repo** and select the repository. Railway picks up `railway.json` automatically.

    The first deploy fails on purpose until a volume is attached at `/data` (`deploy.requiredMountPath`). Without a volume, everything you configure in the UI would be lost on the next redeploy.

    With the CLI instead:

    ```bash
    railway login
    railway init
    railway up --detach
    ```

  </Step>

  <Step title="Attach a volume at /data">
    **Service → Settings → Volumes → Add volume**, mount path `/data`. Or:

    ```bash
    railway volume add --mount-path /data
    ```

    `openclaw.json`, sessions, auth stores, channel state, and the agent workspace all live under `/data` and survive redeploys.

  </Step>

  <Step title="Set the gateway token">
    Add the variable `OPENCLAW_GATEWAY_TOKEN` (your admin secret, for example `openssl rand -hex 32`):

    ```bash
    railway variable set OPENCLAW_GATEWAY_TOKEN=$(openssl rand -hex 32)
    ```

    If you skip this, the bootstrap generates a token, stores it in `openclaw.json`, and prints it once in the deploy logs.

  </Step>

  <Step title="Generate a domain on port 8080">
    **Service → Settings → Networking → Generate Domain**, target port `8080`. Or:

    ```bash
    railway domain --port 8080
    ```

    The Gateway listens on `PORT` when Railway sets it, otherwise on `8080`. Keep the domain's target port and the listening port equal.

  </Step>

  <Step title="Redeploy once">
    Railway injects the domain as `RAILWAY_PUBLIC_DOMAIN` only into deploys started after the domain exists. Redeploy so the bootstrap records it in `gateway.controlUi.allowedOrigins`:

    ```bash
    railway redeploy
    ```

    Until then the first boot enables `gateway.controlUi.dangerouslyAllowHostHeaderOriginFallback` so the UI still loads; the bootstrap warns at every boot while that flag is on. Turn it off in the Control UI after the redeploy.

  </Step>

  <Step title="Connect">
    Open `https://<your-domain>/`, go to **Settings → Connection**, and paste the token. From here on, use the UI.
  </Step>
</Steps>

### Configure everything from the Control UI

After the first boot the only Railway-side settings are the volume, the port, and the initial gateway token. Everything else is in the browser:

- **Settings** groups the common fields per area with an **Advanced** disclosure for the rest; **Settings → Config** renders a form from the live config schema, including plugin and channel schemas, and has a **Raw JSON** editor for anything the form does not cover. See [Configuration](/gateway/configuration).
- **Models and API keys**: **Settings → Models** or the model setup page. Keys are saved to `openclaw.json` on the volume. To keep a key in a Railway variable instead, store a reference such as `{ "source": "env", "provider": "default", "id": "OPENAI_API_KEY" }` under `models.providers.<id>.apiKey` and add the variable in Railway. See [Secrets](/gateway/secrets).
- **Channels** (Telegram, Discord, Slack, WhatsApp, ...): **Settings → Channels**. See [Channels](/channels).
- **Agents, tools, sandboxing, cron, hooks, plugins, MCP servers, skills**: their Settings pages, all backed by the same config file.
- Changes hot-apply where the schema allows it; the UI reports when a Gateway restart is needed. **Settings → Updates** restarts the Gateway.

<Warning>
Some Gateway fields can lock you out of the Control UI if changed on Railway: `gateway.bind` (must stay `lan`), `gateway.auth`, `gateway.controlUi.enabled`, and `gateway.controlUi.allowedOrigins`. If that happens, use `railway ssh` and repair with `openclaw config set` or `openclaw doctor --fix`. The active config lives at `/data/.openclaw/openclaw.json`.
</Warning>

### Environment variables

| Variable                          | Required    | Purpose                                                                                                                                  |
| --------------------------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `OPENCLAW_GATEWAY_TOKEN`          | Recommended | Shared admin secret for the Gateway and Control UI. Without it, a token is generated on first boot, stored in `openclaw.json`, and logged once |
| `OPENCLAW_GATEWAY_PASSWORD`       | Optional    | Use password auth instead of a token on first boot (only when no token is set)                                                           |
| `PORT`                            | Optional    | Listening port; defaults to `8080`. Must match the domain's target port                                                                  |
| `OPENCLAW_PUBLIC_ORIGIN`          | Optional    | Custom domain origin (`https://claw.example.com`) to allow for the Control UI and use as `gateway.publicOrigin`                           |
| `OPENCLAW_CONTROL_UI_ORIGINS`     | Optional    | Comma-separated extra browser origins to allow                                                                                           |
| `OPENCLAW_BASE_IMAGE`             | Optional    | Override the published image the Railway image builds on, for example `ghcr.io/openclaw/openclaw:2026.9.2` or your own build             |
| `OPENCLAW_RAILWAY_SKIP_BOOTSTRAP` | Optional    | Set to `1` to start the Gateway without running the bootstrap                                                                            |

`RAILWAY_PUBLIC_DOMAIN` is injected by Railway and read by the bootstrap; you do not set it.

### Updating

The image pins the OpenClaw version in the `OPENCLAW_BASE_IMAGE` build argument in `Dockerfile.railway`. Bump it in the repo, or set `OPENCLAW_BASE_IMAGE` as a Railway variable (Railway passes service variables to declared Dockerfile build arguments), then redeploy. Startup-safe upgrade migrations run before the Gateway reports ready; see [Updating](/install/updating).

### Recovery and backups

`railway ssh` opens a **root** shell in the container while the Gateway runs as the unprivileged `node` user. Run OpenClaw commands as `node` so the Gateway keeps ownership of its files; the entrypoint also repairs ownership under `/data` on the next redeploy.

```bash
railway ssh
su node -s /bin/sh -c 'openclaw doctor --json'        # read-only deployment preflight
su node -s /bin/sh -c 'openclaw config validate'
su node -s /bin/sh -c 'openclaw backup create'        # exports state, config, auth profiles, workspace
```

Restore verifies and extracts into a fresh staging directory; activation is a separate offline step. See [Restore a full archive](/install/backups#restore-a-full-archive).

## One-click template

<a href="https://railway.com/deploy/clawdbot-railway-template" target="_blank" rel="noreferrer">
  Deploy on Railway
</a>

<Steps>
  <Step title="Deploy the template">
    Click **Deploy on Railway** above.
  </Step>

<Step title="Add a volume">
  Attach a volume mounted at `/data` (required for persistent state).
</Step>

  <Step title="Set variables">
    Set the required **Variables** on the service:

    - `OPENCLAW_GATEWAY_PORT=8080` (required -- must match the port in Public Networking)
    - `OPENCLAW_GATEWAY_TOKEN` (required; treat as an admin secret)
    - `OPENCLAW_STATE_DIR=/data/.openclaw` (required for persistent state)
    - `OPENCLAW_WORKSPACE_DIR=/data/workspace` (required for a persistent workspace)

  </Step>

<Step title="Enable public networking">
  Under **Public Networking**, enable **HTTP Proxy** for the service on port `8080`.
</Step>

  <Step title="Connect">
    Find your public URL in **Railway -> your service -> Settings -> Domains** -- either a generated domain (often `https://<something>.up.railway.app`) or your attached custom domain.

    Open `https://<your-railway-domain>/openclaw` and connect using the configured shared secret. The template uses `OPENCLAW_GATEWAY_TOKEN` by default; if you replace it with password auth, use that password instead.

  </Step>
</Steps>
