Railway runs the Gateway for you and serves the [Control UI](/web/control-ui) on a public HTTPS domain. This is the easiest "no terminal on the server" path: after the first deploy, every OpenClaw setting is changed from the browser.

There are two ways to get there:

- **Deploy from your repository** (recommended): the repo ships `Dockerfile.railway`, a first-boot bootstrap under `deploy/railway/`, and a Railway Infrastructure as Code file at `.railway/railway.ts`. Railway builds a thin image on top of the official OpenClaw image and the bootstrap writes a working `openclaw.json` to the volume.
- **One-click template**: the community template, configured through Railway variables.

## Deploy from your repository

### What the repo provides

| File                           | Purpose                                                                                                                                                                                                                     |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Dockerfile.railway`           | `FROM ghcr.io/openclaw/openclaw:<version>-browser` (Chromium included) plus the bootstrap and the `gog` Google Workspace CLI; builds in seconds instead of compiling the monorepo                                           |
| `deploy/railway/entrypoint.sh` | Hands the root-owned Railway volume to the unprivileged `node` user, keeps auth-profile key material on the volume, clears a gateway lock left by a container Railway stopped uncleanly, then starts the Gateway            |
| `deploy/railway/bootstrap.mjs` | First boot: writes a minimal, schema-valid `openclaw.json`. Every boot: adds a new Railway or custom domain to the Control UI origin allowlist and trusts Railway's edge proxy range when `gateway.trustedProxies` is unset |
| `.railway/railway.ts`          | Infrastructure as Code: the `openclaw` service, the `/data` volume, and the `RAILWAY_DOCKERFILE_PATH` build selector                                                                                                        |

The bootstrap never rewrites a setting you changed in the Control UI, and it leaves any config file it cannot parse as plain JSON untouched.

<Note>
Railway deprecated `railway.json` / `railway.toml` config-as-code: new services cannot use it and existing files stop being read on 2026-12-01. The service settings therefore live in `.railway/railway.ts`, or you set the same two things by hand: the `RAILWAY_DOCKERFILE_PATH=Dockerfile.railway` variable and the `/data` volume. Without the variable Railway builds the root `Dockerfile`, which fails on Railway because it uses BuildKit cache mounts.

Do not configure a Railway healthcheck path. Railway probes only at deploy time, from its edge range without forwarded client headers, and the Gateway rejects that once the range is trusted for real browser traffic (`gateway.trustedProxies`), so the deploy would never go live. The image's own container healthcheck covers liveness.

</Note>

### Steps

<Steps>
  <Step title="Push the repository">
    Push this repository (or your fork) to GitHub. Railway deploys from the branch you select.
  </Step>

  <Step title="Create the project and service">
    With the Railway CLI, from the repository root:

    ```bash
    railway login
    railway init --name openclaw
    railway add --service openclaw \
      --variables "OPENCLAW_GATEWAY_TOKEN=$(openssl rand -hex 32)" \
      --variables "PORT=8080" --variables "OPENCLAW_GATEWAY_PORT=8080"
    ```

    The token is your admin secret for the Gateway and Control UI. If you skip it, the bootstrap generates one, stores it in `openclaw.json`, and prints it once in the deploy logs.

  </Step>

  <Step title="Apply the infrastructure file">
    Railway CLI 4.70 or newer evaluates `.railway/railway.ts`. Install the SDK it imports, preview, then apply. This creates the `/data` volume and the `RAILWAY_DOCKERFILE_PATH` variable:

    ```bash
    npm install --no-save railway
    railway config plan
    railway config apply
    ```

    On an older CLI, set the same things by hand: **Settings → Volumes → Add volume** at `/data` (or `railway volume add --mount-path /data`) and the variable `RAILWAY_DOCKERFILE_PATH=Dockerfile.railway`.

    `openclaw.json`, sessions, auth stores, channel state, and the agent workspace all live under `/data` and survive redeploys.

  </Step>

  <Step title="Generate a domain on port 8080">
    **Service → Settings → Networking → Generate Domain**, target port `8080`. Or:

    ```bash
    railway domain --port 8080
    ```

    The Gateway listens on `PORT` when Railway sets it, otherwise on `8080`. Keep the domain's target port and the listening port equal.

  </Step>

  <Step title="Redeploy once">
    Railway injects the domain as `RAILWAY_PUBLIC_DOMAIN` only into deploys started after the domain exists. Redeploy so the bootstrap records it in `gateway.controlUi.allowedOrigins`:

    ```bash
    railway redeploy
    ```

    Until then the first boot enables `gateway.controlUi.dangerouslyAllowHostHeaderOriginFallback` so the UI still loads; the bootstrap warns at every boot while that flag is on. Turn it off in the Control UI after the redeploy.

  </Step>

  <Step title="Connect and pair the browser">
    Open `https://<your-domain>/`, paste the token when the UI asks for it, and click **Connect**. The first browser then needs one-time device pairing; approve it from a Railway shell (the CLI runs as `node` so the Gateway keeps ownership of its files):

    ```bash
    railway ssh -- sh -c "su node -s /bin/sh -c 'openclaw devices list'"
    railway ssh -- sh -c "su node -s /bin/sh -c 'openclaw devices approve <requestId>'"
    ```

    Reconnect after the approval. From here on, use the UI.

  </Step>
</Steps>

### Configure everything from the Control UI

After the first boot the only Railway-side settings are the volume, the port, and the initial gateway token. Everything else is in the browser:

- **Settings** groups the common fields per area with an **Advanced** disclosure for the rest; **Settings → Config** renders a form from the live config schema, including plugin and channel schemas, and has a **Raw JSON** editor for anything the form does not cover. See [Configuration](/gateway/configuration).
- **Models and API keys**: **Settings → Models** or the model setup page. Keys are saved to `openclaw.json` on the volume. To keep a key in a Railway variable instead, store a reference such as `{ "source": "env", "provider": "default", "id": "OPENAI_API_KEY" }` under `models.providers.<id>.apiKey` and add the variable in Railway. See [Secrets](/gateway/secrets).
- **OpenRouter model ids**: choose concrete ids such as `openrouter/deepseek/deepseek-v4-flash`. The `~vendor/model-latest` aliases in the catalog can have no serving endpoints, in which case the connection probe reports a generic failure even though the key is valid.
- **DeepSeek V4 probe failures**: the provider probe sends an 8-token prompt, and DeepSeek V4 reasons by default, so the probe can return no visible text and show "Connection failed" while chat works. To make the probe pass, disable reasoning for that model under **Settings → Config**: `agents.defaults.models["openrouter/deepseek/deepseek-v4-flash"].params.extra_body.reasoning.enabled = false`. This also turns off hidden reasoning for chat replies with that model.
- **Channels** (Telegram, Discord, Slack, WhatsApp, ...): **Settings → Channels**. See [Channels](/channels).
- **Agents, tools, sandboxing, cron, hooks, plugins, MCP servers, skills**: their Settings pages, all backed by the same config file.
- Changes hot-apply where the schema allows it; the UI reports when a Gateway restart is needed. **Settings → Updates** restarts the Gateway.

<Warning>
  Some Gateway fields can lock you out of the Control UI if changed on Railway: `gateway.bind` (must
  stay `lan`), `gateway.auth`, `gateway.controlUi.enabled`, and `gateway.controlUi.allowedOrigins`.
  If that happens, use `railway ssh` and repair with `openclaw config set` or `openclaw doctor
  --fix`. The active config lives at `/data/.openclaw/openclaw.json`.
</Warning>

### Browser, web search, and Google Sheets

The Railway image is the `-browser` variant of the official image, so Chromium is already installed, and the bootstrap writes `browser.headless` and `browser.noSandbox` for the container. The agent's `browser` tool works without any setup: ask it to open a page and it drives an isolated headless Chromium on the Gateway. The Control UI **Browser** panel shows what it is doing. Screenshots need a vision-capable model; snapshots and page text do not.

Web search defaults to DuckDuckGo, the only key-free provider. For better results, add a [Brave Search](/tools/brave-search) key under **Settings → Config → tools.web.search** or as the `BRAVE_API_KEY` variable.

Google Sheets, Drive, Docs, Gmail, and Calendar go through the `gog` CLI, which is baked into the image and backs the bundled `gog` skill. It talks to Google as you, through your own OAuth client, and keeps its encrypted tokens under `/data/gogcli`, so the authorization survives redeploys. One-time setup:

<Steps>
  <Step title="Create a Google OAuth client">
    In [Google Cloud Console](https://console.cloud.google.com/projectcreate) create a project, enable the **Google Sheets API** and **Google Drive API** (plus Docs or Gmail if you want them), configure the OAuth consent screen as **External** with your email, then create an **OAuth client ID** of type **Desktop app** and download its JSON. Under **Audience**, click **Publish app** so refresh tokens do not expire after seven days.
  </Step>

<Step title="Give the client to the Gateway">
  Store the downloaded JSON as the `GOG_CLIENT_SECRET_JSON` variable in Railway (paste the whole
  file as the value). The entrypoint hands it to `gog` on every boot; Railway redeploys when the
  variable is added.
</Step>

  <Step title="Authorize your Google account once">
    From a Railway shell, run the browserless flow. The first command prints a URL; open it on your computer, approve access, and paste the address of the page Google redirects you to into the second command:

    ```bash
    railway ssh -- sh -c "su node -s /bin/sh -c 'gog auth add you@gmail.com --services sheets,drive --remote --step 1'"
    railway ssh -- sh -c "su node -s /bin/sh -c 'gog auth add you@gmail.com --services sheets,drive --remote --step 2 --auth-url \"<redirect url>\"'"
    railway ssh -- sh -c "su node -s /bin/sh -c 'gog auth doctor --check --no-input'"
    ```

    From then on the agent can read, append, and update sheets by their spreadsheet id. Share a sheet's id with it, or ask it to create one in Drive.

  </Step>
</Steps>

### Environment variables

| Variable                          | Required    | Purpose                                                                                                                                                                                                        |
| --------------------------------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RAILWAY_DOCKERFILE_PATH`         | Required    | `Dockerfile.railway`; set by `.railway/railway.ts`. Tells Railway which Dockerfile to build                                                                                                                    |
| `OPENCLAW_GATEWAY_TOKEN`          | Recommended | Shared admin secret for the Gateway and Control UI. Without it, a token is generated on first boot, stored in `openclaw.json`, and logged once                                                                 |
| `OPENCLAW_GATEWAY_PASSWORD`       | Optional    | Use password auth instead of a token on first boot (only when no token is set)                                                                                                                                 |
| `PORT`, `OPENCLAW_GATEWAY_PORT`   | Recommended | Set both to `8080` so Railway's router, the Gateway, and the CLI in `railway ssh` sessions agree on one port. Without them Railway injects a random `PORT` and CLI commands need `OPENCLAW_GATEWAY_PORT=$PORT` |
| `OPENCLAW_PUBLIC_ORIGIN`          | Optional    | Custom domain origin (`https://claw.example.com`) to allow for the Control UI and use as `gateway.publicOrigin`                                                                                                |
| `OPENCLAW_CONTROL_UI_ORIGINS`     | Optional    | Comma-separated extra browser origins to allow                                                                                                                                                                 |
| `OPENCLAW_TRUSTED_PROXIES`        | Optional    | Comma-separated proxy IPs or CIDRs for `gateway.trustedProxies`. Defaults to Railway's edge range `100.64.0.0/10`, without which the Gateway rejects all proxied requests                                      |
| `OPENCLAW_BASE_IMAGE`             | Optional    | Override the published image the Railway image builds on. Defaults to the `-browser` variant; use `ghcr.io/openclaw/openclaw:2026.9.2` for a smaller image without Chromium, or your own build                 |
| `OPENCLAW_RAILWAY_SKIP_BOOTSTRAP` | Optional    | Set to `1` to start the Gateway without running the bootstrap                                                                                                                                                  |
| `GOG_CLIENT_SECRET_JSON`          | Optional    | Google Desktop OAuth client JSON for the `gog` CLI (Sheets, Drive, Docs, Gmail, Calendar); stored for `gog` at every boot                                                                                      |
| `GOG_KEYRING_PASSWORD`            | Optional    | Password for `gog`'s encrypted token keyring. When unset, one is generated on first boot and kept at `/data/gogcli/.keyring-password`; set it in Railway to keep it off the volume                             |

`RAILWAY_PUBLIC_DOMAIN` is injected by Railway and read by the bootstrap; you do not set it.

### Updating

The image pins the OpenClaw version in the `OPENCLAW_BASE_IMAGE` build argument in `Dockerfile.railway`. Bump it in the repo, or set `OPENCLAW_BASE_IMAGE` as a Railway variable (Railway passes service variables to declared Dockerfile build arguments), then redeploy. Startup-safe upgrade migrations run before the Gateway reports ready; see [Updating](/install/updating).

### Recovery and backups

`railway ssh` opens a **root** shell in the container while the Gateway runs as the unprivileged `node` user. Run OpenClaw commands as `node` so the Gateway keeps ownership of its files; the entrypoint also repairs ownership under `/data` on the next redeploy.

```bash
railway ssh
su node -s /bin/sh -c 'openclaw doctor --json'        # read-only deployment preflight
su node -s /bin/sh -c 'openclaw config validate'
su node -s /bin/sh -c 'openclaw backup create'        # exports state, config, auth profiles, workspace
```

Restore verifies and extracts into a fresh staging directory; activation is a separate offline step. See [Restore a full archive](/install/backups#restore-a-full-archive).

## One-click template

<a href="https://railway.com/deploy/clawdbot-railway-template" target="_blank" rel="noreferrer">
  Deploy on Railway
</a>

<Steps>
  <Step title="Deploy the template">
    Click **Deploy on Railway** above.
  </Step>

<Step title="Add a volume">
  Attach a volume mounted at `/data` (required for persistent state).
</Step>

  <Step title="Set variables">
    Set the required **Variables** on the service:

    - `OPENCLAW_GATEWAY_PORT=8080` (required -- must match the port in Public Networking)
    - `OPENCLAW_GATEWAY_TOKEN` (required; treat as an admin secret)
    - `OPENCLAW_STATE_DIR=/data/.openclaw` (required for persistent state)
    - `OPENCLAW_WORKSPACE_DIR=/data/workspace` (required for a persistent workspace)

  </Step>

<Step title="Enable public networking">
  Under **Public Networking**, enable **HTTP Proxy** for the service on port `8080`.
</Step>

  <Step title="Connect">
    Find your public URL in **Railway -> your service -> Settings -> Domains** -- either a generated domain (often `https://<something>.up.railway.app`) or your attached custom domain.

    Open `https://<your-railway-domain>/openclaw` and connect using the configured shared secret. The template uses `OPENCLAW_GATEWAY_TOKEN` by default; if you replace it with password auth, use that password instead.

  </Step>
</Steps>
